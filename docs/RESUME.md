## 2. 项目描述（可直接粘贴到简历「项目经历」）

**GoVulnLab｜个人项目｜Go / MySQL / Redis / Docker**

- 使用 Go 标准库（`net/http` + Go 1.22 ServeMux 方法路由）实现注册登录、订单、留言板、审计、后台管理，
  按 `cmd / internal / migrations / web` 分层，依赖显式注入，模板与 SQL 通过 `go:embed` 打进单二进制。
- 设计并实现完整会话体系：Redis 集中式会话（明确放弃 JWT 以获得可撤销性），登录与改密时销毁旧会话并签发新 ID 防会话固定；
  Cookie 采用 `HttpOnly + SameSite=Lax`，生产可切 `Secure`。
- 实现 Web 安全纵深防御：全参数化 SQL、`html/template` 上下文转义 + CSP per-request nonce、
  会话内同步 CSRF Token（常量时间比较 + Origin 校验）、订单归属校验下推 SQL 并将越权统一返回 404、
  bcrypt cost=12 + Redis 失败计数锁定 + 等时比较抗账号枚举与时序侧信道。
- 用 Redis Lua 脚本实现原子令牌桶限流（全局桶 + 登录桶双策略），配合 1MiB 请求体限制、
  服务端读写/空闲超时与 `ReadHeaderTimeout` 抵御慢速攻击与资源耗尽。
- 订单创建/取消与审计日志同事务提交，避免"业务成功但审计缺失"；审计记录携带 `request_id`，
  可与访问日志对账，形成 request_id 贯穿的可观测链路。
- 工程化交付：`//go:embed` 迁移器（自研 SQL 拆分，拒绝开启 `multiStatements` 以缩小注入面）、
  幂等 seed、`/healthz` 与 `/readyz` 分层探针、`signal.NotifyContext` 优雅关闭、
  Dockerfile（多阶段 + 非 root + healthcheck）、docker compose、systemd 加固单元、Nginx TLS 反代、
  GitHub Actions（gofmt + vet + `-race` 测试 + 构建 + 镜像构建）、PowerShell/Bash 双份端到端冒烟脚本。

## 3. STAR 版（面试口述用，控制在 90 秒）

**S（背景）**
我最初想做一个"能练 Web 漏洞"的项目，但写完发现它只是几个飘着 `fmt.Println` 的漏洞页：没有事务、没有会话管理、
连表结构都有三套互相矛盾的版本（MySQL 迁移脚本、SQLite 脚本、代码里的 `CREATE TABLE`）。
这种项目既不能证明我懂安全，也不能证明我能写工程代码。

**T（任务）**
把它重做成一个"既能对照学习 5 类漏洞、又能按生产标准部署"的完整项目，并且要在真实 MySQL + Redis 上跑通全流程。

**A（行动）**
1. 先做诊断：逐文件读完旧代码，列出 30+ 处缺陷（含 `Content‑Type` 用了 Unicode 连字符导致响应头永远设不上、
   `audit_log` 查表名与插入表名不一致、`FROM orders o, LEFT JOIN` 语法错、handler 漏 `return` 等）。
2. 重定分层：`handler → service → store` 单向依赖，基础包（config/logger/apperr/reqctx/session/httpx）不反向依赖业务。
3. 安全落地：参数化 SQL、模板自动转义 + CSP nonce、CSRF Token、越权 404、登录锁定、会话轮换、
   Redis Lua 原子限流，每一项都指出具体代码位置。
4. 工程交付：embed 迁移 + 幂等 seed + 探针 + 优雅关闭 + Docker/systemd/Nginx + CI + 端到端脚本。
5. 验证：`go build/vet/test` 全绿，真实库上跑 26 项 HTTP 断言，实测登录第 6 次返回 429。

**R（结果）**
一个 51 个 Go 文件、约 3.6k 行、20 个模板、16 个包的单二进制项目；
5 类漏洞都能"复现 + 指出修复代码 + 用脚本断言修复有效"；
面试时可以在 3 分钟内从首页点到靶场再点到审计，全程有据可查。

## 6. 五个可以主动抛出的亮点

1. **"同一套业务，两份实现"**
   业务代码是安全的，靶场代码是故意不安全的，两者在同一仓库、可逐行对照。
   这比"我做过一个漏洞靶场"更能说明你真的理解漏洞成因与修复边界。

2. **拒绝 `multiStatements`**
   很多人为了跑迁移脚本会直接开 `multiStatements=true`，但那会把 SQL 注入的危害从"改一条查询"放大到"执行任意语句"。
   我的做法是迁移器自己按分号拆分（跳过注释、忽略字符串内的分号），运行期连接保持单语句执行。

3. **会话设计是"反 JWT"的**
   JWT 无状态但不可撤销；这个系统需要"改密即踢下线""管理员能封号"，所以选 Redis 会话。
   并且登录/改密都会销毁旧会话、签发新 ID，直接消灭会话固定攻击。

4. **审计与业务同事务**
   订单写成功但审计写失败，等于事后无法追责。两者同事务提交，任一步失败整体回滚。

5. **限流是原子的**
   令牌桶用 Redis Lua 脚本一次完成"取令牌 + 回填时间戳"，避免"读-改-写"在并发下超发；
   登录接口单独一个桶，容量刻意大于锁定阈值，让"账号级锁定"先触发，提示更精确。

## 7. 高频追问与回答（建议背熟前 6 个）

**Q1：为什么不用 JWT？**
A：这个系统需要可撤销性。用户改密、管理员封号时，JWT 只能靠黑名单，而黑名单又引入中心存储，
等于把 JWT 的最大优点（无状态）抵消掉。Redis 会话删 key 即失效，还能天然支持会话固定防护（登录换 ID）。
JWT 更适合服务间调用、短生命周期凭证。

**Q2：SQL 注入你是怎么修的？怎么证明修好了？**
A：全部改为参数化查询（`?` 占位符），输入作为参数传输而不是拼进 SQL。
证明分两层：靶场 `/lab/sqli` 用同样 payload 能登录成功（说明漏洞真实存在）；
业务 `/auth/login` 用同样 payload 返回"用户名或密码错误"，且不返回任何 SQL 报错。
另外全项目 `grep "Sprintf.*SELECT"` 只会命中靶场那一处，review 时能快速确认没有扩散。

**Q3：XSS 防护里，转义和 CSP 分别起什么作用？**
A：转义是第一道防线，保证用户输入永远不会变成 HTML 结构；CSP 是兜底，即使某处漏了转义，
注入的 `<script>` 因为没有 nonce 也不会执行。两者不能互相替代：只靠 CSP 挡不住 `javascript:` 伪协议之类，
只靠转义则一旦漏一处就直接失守。

**Q4：CSRF 为什么不用「双提交 Cookie」，而是会话内 Token？**
A：双提交依赖"攻击者读不到 Cookie"，但一旦存在子域 XSS 或 Cookie 注入，就可能被绕过。
会话内 Token 存在服务端，攻击者既读不到 Cookie（HttpOnly）也读不到会话内容，服务端强校验，更可靠。
我另外加了 Origin 校验做纵深防御，并且 Cookie 用 `SameSite=Lax`。

**Q5：越权为什么返回 404 而不是 403？**
A：403 等于告诉攻击者"这个 id 存在，只是不属于你"，本身就是信息泄露，还能被用来枚举有效 id。
404 让"不存在"和"不属于你"对外表现一致。

**Q6：登录锁定是怎么实现的？为什么 key 里用户名要哈希？**
A：Redis 计数，key 是 `ip + sha256(用户名)[:8]`，达到 5 次锁定 15 分钟，登录成功清零。
哈希是因为 Redis key 可能被 `--scan` 导出到监控面板，明文用户名会泄露"谁正在被撞库"。
另外用户不存在时也跑一次等时 bcrypt，抹平响应时间差，防账号枚举。

**Q7：限流为什么用 Lua？**
A：令牌桶需要"读剩余令牌 → 判断 → 扣减 → 回填时间戳"四步，分开执行在并发下会超发。
Lua 在 Redis 里单线程原子执行，一次调用完成全部逻辑，多个应用实例共享同一个桶。

**Q8：如果现在要上生产，你还缺什么？**
A：① 关掉靶场（`GVL_LAB_ENABLED=false`）；② 开 `session.secure` 与 `trust_proxy`（前面必须有 Nginx）；
③ 审计改异步 + 分区（现在是同步写库，高并发会成写热点）；④ 加 `/metrics` 和 `govulncheck`；
⑤ 做备份与恢复演练。这些我在 `docs/DEPLOY.md` 和 `docs/SECURITY.md` 的"剩余风险"里都列了。

**Q9：为什么不引框架（gin/echo）？**
A：这个规模下标准库够用，而且中间件顺序、状态码记录、超时、优雅关闭这些细节，只有自己写一遍才真的掌握。
依赖少也意味着供应链风险小、审计面小。Go 1.22 的 `POST /orders/{id}/cancel` 路由已经解决了我需要的路径参数问题。

**Q10：这个项目最大的难点是什么？**
A：不是写某个功能，而是"让安全措施不互相打架"。比如登录限流和账号锁定都会返回 429，
如果限流桶太小，锁定逻辑永远触发不了，用户看到的提示就不精确；再比如 CSRF 中间件要读表单，
就必须在 BodyLimit 之后、handler 之前，顺序错了要么读不到 Token，要么内存被撑爆。
这类"顺序与阈值"的取舍，是我做完这个项目收获最大的部分。

## 8. 三分钟演示动线（现场/视频面试）

1. `http://127.0.0.1:8080` 首页 → 讲项目定位（安全实现 + 漏洞对照）

9. 收尾：`docs/` 四份文档 + `scripts/smoke.ps1` 的 26 项断言
